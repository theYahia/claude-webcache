## BLOCKERS

### B1 — STRICT_REDACT=1 causes cache key collisions across authenticated requests

File: plugin/src/cache.js:208-212

When WEBCACHE_STRICT_REDACT=1, makeKey passes the URL through redactUrl before hashing. redactUrl replaces known credential query params (e.g., token, api_key) with the literal string ***. This means https://api.example.com/data?token=userA and https://api.example.com/data?token=userB produce the identical cache key. The first response cached is silently returned to both users on subsequent lookups.

The flag name implies a stricter security posture, but it creates cross-request data leakage. A user enabling STRICT_REDACT to protect credentials in the hash is actually introducing response poisoning for any endpoint that differentiates users via URL query params.

Fix: Remove the STRICT_REDACT key-hashing path entirely. If collision-by-design is intentional (same endpoint = shared response regardless of caller), document it explicitly as "shared cache mode", warn that it must not be used for per-user authenticated endpoints, and add a runtime log when a credential param is detected in the URL.

### B2 — cache_store MCP tool enables cross-session prompt injection cache poisoning

File: plugin/scripts/mcp-server.cjs:165-175

cache_store accepts an arbitrary output string and writes it to the SQLite cache without validating that the content originated from an actual WebFetch response. A Claude session that calls cache_store with adversarial text in output poisons the cache. All future sessions that call cached_fetch for that URL+prompt receive the injected content as a trusted MCP tool response, indistinguishable from a real fetch result. This persists indefinitely across sessions, unlike a single-session WebFetch exposure.

Fix: No reliable provenance check is possible at the MCP layer since Claude generates the output argument. Minimum mitigations: (1) add a source field to cache rows distinguishing hook-writes from manual MCP writes so cache_list can surface provenance; (2) document explicitly that cache_store is a write path reachable by adversarial prompts and should be treated as untrusted input storage.

## WARNINGS

### W1 — Live GitHub OAuth token on disk in project directory

File: .mcpregistry_github_token (line 1)

A GitHub personal access token (gho_ prefix) is written as plaintext in the project root. It is .gitignore'd (.mcpregistry_* pattern at .gitignore:12) and confirmed absent from the git index. However, it sits in a directory that may be synced, backed up, or readable by other local processes. There is no expiry metadata in the file and no code that warns about token age. The JWT in .mcpregistry_registry_token has an exp field (approximately May 2026) but nothing reads or enforces it before use.

Fix: Delete both files after one-time use. If persistence is required, store in a secrets manager or at minimum in ~/.config/ with restricted permissions (not inside a project directory). Add a cleanup note to CONTRIBUTING.md.

---

### W2 — cached_fetch returns raw web content as an indistinguishable trusted tool response

File: plugin/scripts/mcp-server.cjs:158-161

cached_fetch returns the full cached WebFetch output with no wrapper identifying it as external web content. WebFetch responses arrive with Claude Code's built-in signal that content is from the web. Cached responses arrive indistinguishably from native tool output and persist across sessions indefinitely. An attacker who influenced what was cached (e.g., by injecting content into a site before its first fetch) gets a persistent injection that outlasts all future sessions hitting that cache key.

Fix: Prepend a delimiter to the returned text, e.g., "[CACHED WEB CONTENT from {url}, fetched {date}]", so the model's context makes source and age explicit and the model can reason about provenance.

## NITS

### N1 — PRAGMA table_info SQL string interpolation

File: plugin/src/cache.js:123

tableHasColumn interpolates the table argument directly into a PRAGMA string without sanitization. Currently always called with the hardcoded literal 'cache' (line 187), so not exploitable. The function signature accepts any string -- a future caller passing user-controlled input would introduce a SQL injection path. Fix: validate table against an allowlist (['cache','meta','meta_str']) before interpolating.

### N2 — Dashboard 500 handler leaks e.message

File: plugin/scripts/dashboard.cjs:272

res.end(e.message) exposes internal error text (DB paths, schema errors) over HTTP. Mitigated by server.listen(port, '127.0.0.1') at line 276. Low risk as-is, but if the dashboard is ever proxied (ngrok, VS Code port forwarding) this becomes an info-disclosure channel. Fix: return a generic string and log the full error to stderr.

## Verdict

NEEDS-WORK

Two blockers require fixing before broader distribution: B1 (STRICT_REDACT collision) is a silent per-user response leakage trap behind a misleadingly-named flag; B2 (cache_store as open write path) enables persistent cross-session prompt injection that outlasts any single WebFetch exposure. Both are fixable without architectural changes. Delete the token files (W1) immediately.
